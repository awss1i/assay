## <a id="how-the-code-is-laid-out"></a>Как устроен код

**`src/assay/`**, сам инструмент:

- `browser.py` раздаёт папку, открывает страницу, ждёт её загрузки и читает пиксели, текст, поля ввода и стили. Он только измеряет и никогда не решает, провалено ли что-то.
- `surface.py` превращает отрисованную страницу в список элементов управления (control) и строит план проверок (check).
- `run.py` содержит `check()`, который запускает всё, и `judge()`, который сравнивает страницу до и после каждой проверки и решает, пройдена ли она. Большинство правил (rule) находится здесь.
- `qa.py` выполняет план и хранит результаты. В нём нет кода для браузера, поэтому его можно тестировать без браузера.
- `links.py` группирует провалы, которые являются одним и тем же замечанием (finding). Он читает готовые результаты и никогда не меняет результат.
- `report.py` записывает страницу для `--report`.
- `tint.py` отвечает за цвет в терминале.
- `cli.py` является командой `assay`.

**`plugins/assay/`**, skill и плагин (plugin):

- `skills/checking-a-page/` является skill и состоит из одного файла в формате Markdown.
- `hooks/pages.py` находит страницы, изменённые за ход (turn), по времени изменения файлов.
- `hooks/check_pages.py` проверяет их и всегда сообщает результат.

**`benchmarks/`**, страницы, по которым оценивают assay:

- `generated/` содержит программы, написанные ИИ, и эталоны (answer key) к ним.
- `planted/` содержит рабочие программы и их копии с внедрёнными багами (planted bug).
- `harness/` содержит два скрипта оценки и эталон для группировки замечаний.

**`tests/`** содержит набор тестов. **`docs/`** содержит документацию и скрипты, которые рисуют картинки для README по настоящим запускам.

## <a id="changing-a-rule"></a>Изменение правила

Правилом называется всё, что решает, провалена ли проверка. Большинство правил находится в `judge` в файле `run.py`, а проверки, которые их задействуют, строятся в `surface.py`.

1. **Напишите два теста.** Первый содержит страницу, которую правило должно пометить, а второй содержит страницу, которую оно помечать не должно. Чистые сравнения помещайте в `tests/test_judge.py`, которому не нужен браузер. Всё, чему нужна настоящая страница, помещайте в `tests/test_end_to_end.py`.
2. **Запустите оба бенчмарка** и укажите в пулреквесте числа до и после изменения. Тесты не видят ложного срабатывания (false alarm) на рабочей программе, а бенчмарки видят.
3. **Ложное срабатывание обходится дороже пропуска (miss).** Правило, которое ловит на три бага больше, но помечает одну рабочую страницу, улучшением не считается, потому что из-за ложного срабатывания кто-то начнёт менять правильный код.
4. **Опишите, что произошло, простыми словами.** Сообщение говорит, что сделал assay и как на это отреагировала страница, например *when pressed twice from the same starting point, this changed nothing on the first press and changed the page on the second, so it reacts one press late* (при двух нажатиях из одного и того же состояния первое ничего не изменило, а второе изменило страницу, поэтому реакция опаздывает на одно нажатие). Сообщение никогда не выносит голый вердикт вроде *this page is broken* (эта страница сломана) и должно быть понятно тому, кто не читал правило.
5. **Задокументируйте правило.** Добавьте его в `docs/how-it-works.md` под действием, которое его вызывает, и опишите, что делает assay, какое сообщение он выводит и когда он молчит и почему.

Для исправления ложного срабатывания нужна страница, которая была помечена. Её добавляют как тест, который должен оставаться чистым.

## <a id="tests"></a>Тесты

```bash
pytest -q
```

Полный набор тестов занимает около 25 минут, потому что большинство тестов управляют настоящим браузером. `tests/test_judge.py`, `tests/test_plan.py`, `tests/test_links.py`, `tests/test_perform.py` и `tests/test_translations.py` не требуют браузера и выполняются за секунды, поэтому во время работы запускайте их. Больше всего времени занимает `tests/test_end_to_end.py`, и без браузера он пропускается, а не проваливается.

CI запускает весь набор на Python 3.10, 3.11, 3.12, 3.13 и 3.14 для каждого пулреквеста, а также короткий прогон обоих скриптов оценки бенчмарков. Всё это должно пройти до слияния.

Для исправления бага нужен тест, который не проходит до исправления и проходит после него.

## <a id="benchmarks"></a>Бенчмарки

```bash
python benchmarks/harness/generated.py    # сгенерированный набор
python benchmarks/harness/planted.py      # набор с внедрёнными багами
```

Изменение правила или папки `benchmarks/` требует запустить оба скрипта оценки до и после изменения. Каждый выводит строку со сводкой, и обе строки нужно указать в пулреквесте. Изменение считается улучшением, только если оно находит больше багов и не помечает ни одной рабочей страницы.

Суждения в эталонах записаны вручную. Если из-за вашего изменения assay сообщает что-то новое о программе из бенчмарка, скрипт оценки ничего не запишет, пока вы не укажете, чем является новое замечание.

## <a id="adding-a-harness"></a>Добавление harness

- **Если harness (среда запуска агента) читает файлы skill,** добавьте шаги его установки в `docs/harnesses.md` и укажите в них `plugins/assay/skills/checking-a-page/`.
- **Если у него свой формат плагинов,** добавьте его файл marketplace рядом с остальными (`.claude-plugin/`, `.cursor-plugin/`, `.grok-plugin/`, `.agents/plugins/`, `.github/plugin/`) и опишите его там же.
- **Проверьте его в самом harness** и укажите, какую версию вы использовали.
- **Обновите число.** README, страница установки, страница о harness и README плагина называют число поддерживаемых harness.
- **Он сообщает и никогда не исправляет.** Skill и плагин передают, что было нажато и что произошло, и не правят из-за этого код. Сохраняйте это поведение.

## <a id="changing-the-docs"></a>Изменение документации

Документация ведётся также на упрощённом китайском, японском, корейском и русском языках. Меняйте только английский текст. После этого `tests/test_translations.py` перестанет проходить, и это ожидаемо, а мейнтейнер обновит переводы до слияния изменения.
